故障排查
========================================

先确认问题发生在 Web 工作台还是旧版脚本。两者管理的容器和记录相互独立，
Web 实验不依赖旧脚本的 ``.frr_containers.tmp`` 或同名 netns 登记。

   :local:
   :depth: 2

启动与浏览器访问
----------------------------------------

.. list-table::
   :header-rows: 1
   :widths: 32 68

   * - 现象
     - 处理方法
   * - 提示缺少 docker、ip、nsenter，或只能设计拓扑
     - 在 Linux Docker 宿主机安装所需命令，以 root 启动后端且不带 --preview。Windows 上的设计模式后端不能创建 Linux veth。
   * - ModuleNotFoundError 或找不到 FastAPI/Uvicorn
     - 用项目虚拟环境安装 requirements.txt，并通过同一个虚拟环境的 Python 启动；不要改用系统 sudo python3。
   * - 首页提示缺少前端构建产物
     - 构建 web/dist，或用 --web-dir 指向已有产物；仅安装 npm 依赖不会生成页面。
   * - 其他电脑无法访问 8090
     - 检查后端是否使用 --host 0.0.0.0、进程是否存活及该端口是否可达；浏览器填写宿主机 IP，不能填写客户端自己的 127.0.0.1。
   * - 访问令牌无效 / Unauthorized
     - 使用当前后端终端打印的令牌。未设置固定令牌时，每次重启都会变化；确认浏览器连接的是预期端口和后端。
   * - 5173 页面能打开，但 API 请求失败
     - Vite 不代替后端。检查 Python 后端是否启动，以及 web/.env.local 的 ROUTE_OVS_API_TARGET 是否指向它。
   * - 数据目录已被另一个后端占用
     - 找到使用该目录的原后端，继续使用它或正常停止后再启动。不要通过删除锁文件让两个后端同时管理同一目录。
   * - 更新代码后页面或行为没有变化
     - 前端源码需重新构建并刷新；Python 代码需重启后端；本地抓包启动器需重新下载安装。详见 :ref:`workbench-start`。

完整安装和启动命令见 :ref:`workbench-start`。后端运行时显示的部署环境检查结果针对
**后端所在主机**，不是浏览器电脑；只在 Windows 安装 Docker CLI 不能修复 Linux 后端的缺失依赖。

Vite / Rolldown 原生依赖错误
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

出现 ``Cannot find native binding``、缺少 ``@rolldown/binding-linux-x64-gnu`` 等错误时，
先检查 Node.js 版本及依赖安装的平台。当前项目要求 Node.js 22.12+ 的 22.x 或 24+，
建议使用 Node.js 24 LTS；旧的 Node.js 20 环境需先升级。

在实际运行 Vite 的系统中，从项目根目录执行::

  node --version
  npm --prefix web ci --include=optional
  npm --prefix web run build

``npm ci`` 会按现有锁文件重建 ``web/node_modules``，不需要删除 ``package-lock.json``。
不要把 Windows 的 node_modules 复制到 Linux，也不要在 Samba 共享目录中同时由两个系统使用它。
若仍失败，检查安装日志中的下载错误、代理和平台架构；构建产物 ``web/dist`` 可以跨平台复制。

部署、镜像与连通性
----------------------------------------

.. list-table::
   :header-rows: 1
   :widths: 32 68

   * - 现象
     - 处理方法
   * - 镜像不存在或拉取失败
     - 核对实际标签和 Docker 平台；可从镜像管理上传项目归档。私有仓库登录需使用后端运行账户，普通用户的 Docker 登录未必适用于 root 后端。
   * - 镜像加载成功，设备仍无法启动
     - 检查所选模板与镜像是否兼容，以及部署日志中的启动命令。绑定 FRR 模板不会让任意镜像自动具备 FRR、vtysh 或对应文件路径。
   * - 上传或 Dockerfile 构建失败
     - 查看镜像任务日志、归档格式、上传大小、Dockerfile 路径和构建上下文。使用 docker save 归档；构建上下文的 COPY 文件需位于正确的相对路径。
   * - 无法删除镜像
     - 已保存实验或现存容器引用的镜像受到保护。先核对引用，再按需要修改实验或清理设备；共享镜像层也可能仍被其他标签使用。
   * - 部署失败或状态为“需要检查”
     - 查看底部部署日志和实际容器、接口状态。外部重启容器会改变网络命名空间，原网线可能已丢失；核对配置保存情况后清理并重新部署。
   * - 清理未完成
     - 恢复 Docker 连接后重试，核对报错中设备的归属。保留实验记录便于继续清理，不要直接删除数据文件来隐藏错误。
   * - 端口不存在
     - 画布上的空闲插槽尚未创建 veth；只有接好网线并部署后，接口才会出现在容器中。
   * - ping 不通
     - 依次检查接口状态、地址/掩码、同网段网关、路由和 FRR 协议；交换机 STP 刚启动时需要等待收敛。必要时抓取 ARP/ICMP。
   * - 部署后不能添加注释或修改设备配置
     - 部署后允许移动已有设备和注释、自动对齐及保存布局；增删对象、修改内容/配置或网线仍需清理设备。部署、清理或保存进行中也会暂时锁定布局。
   * - 普通滚轮不再缩放拓扑
     - 普通滚轮用于上下平移，Shift＋滚轮左右平移；按住 Ctrl 再滚动可缩放。也可拖动画布横纵滚动条或使用左上角缩放按钮。
   * - 保存布局提示未知 API
     - 前后端需要一起更新；重新构建前端并重启 Python 后端，再刷新页面。布局保存使用新的 /api/labs/{id}/layout 接口。
   * - 找不到设备拉伸手柄
     - 设备已改为紧凑圆形图标，按端口数量自动调整；手动拉伸入口已移除。可通过顶部自动对齐整理布局。
   * - 端口在圆周上的位置变了
     - 连线优化会根据对端方向调整图形插槽，实际接口名称和连接关系没有变化。悬浮端口可查看对端。
   * - 注释保存后刷新不见了
     - 确认点击了项目“保存”，并且前后端都已更新、后端已重启。旧后端不能保留新增的注释字段。
   * - 侧边栏看不到了，或窗口变窄后宽度变小
     - 点击两侧窄栏的箭头展开；拖动与画布之间的竖线调宽，双击恢复默认。窗口较窄时会限制宽度以保留画布空间。
   * - 刷新后侧边栏设置没有保留
     - 确认使用同一浏览器和工作台地址，并允许本地存储。布局偏好不保存在实验文件中。

可在 Docker 宿主机查看 ``sudo docker ps -a``，在对应设备的 Web Shell 中查看
``ip -br addr`` 和 ``ip route``。Web 使用容器网络命名空间，
``ip netns list`` 没有显示同名条目并不代表部署失败。

终端、配置与实验文件
----------------------------------------

* 双击设备无法打开终端：先确认设备处于运行中，并查看部署日志。FRR 默认进入 vtysh；
  VPCS/交换机使用 Linux sh，不能直接输入厂商 CLI 或经典 VPCS 命令。
* 网页刷新后原命令不见：刷新会结束原终端连接；重新打开后是新会话，设备仍可继续运行。
* FRR 保存失败：查看逐台结果，检查已启用协议进程是否正常、共享目录权限和镜像兼容性。
  有失败设备时不要直接清理整个实验；“查看磁盘配置”可核对已有文件。
* 清理后配置丢失：拓扑“保存”不会执行 FRR 保存命令。清理前点击“保存设备配置”，
  或在 FRR 终端写入共享文件；导出 JSON 前仍需点击“保存设备配置”同步文本。
* VPCS/交换机的 Shell 配置没有恢复：目前只恢复拓扑中的地址、网关和桥接关系，
  任意 Shell 操作、文件或进程尚不支持通用保存。
* 导入 JSON 后原实验被更新：当前导入保留实验 ID，改名称不会创建独立副本。
  复制实验及完整备份方法见 :doc:`workbench-data`。
* 已部署项目需要改名：点击顶部项目名称即可；不必清理设备。若提示等待，先完成当前部署、清理或保存操作。
* 改名后仍显示有未保存修改：重命名只保存名称；尚未保存的拓扑和设备属性需要另外保存。
* 改名提示未知 API：更新 Python 后端后需要重启；只构建前端不能加载新的重命名接口。
* 删除实验按钮不可用：已部署实验需先清理；没有设备、网线或待保存内容的空白草稿无需删除。

FRR 保存与清理后恢复的完整验证流程见 :ref:`workbench-frr-config`。
“导出 JSON”不包含全部设备配置文件、镜像及容器可写层，不能代替完整数据备份。

Wireshark 没有窗口、等待 SSH 或找不到文件
------------------------------------------------------------

按 :doc:`workbench-capture` 的状态表排查：

* “准备抓包”之后还需点击“打开本机 Wireshark”，并允许浏览器打开本地应用。
* 没有私钥也可使用密码认证：关闭自动开始，在 Wireshark 的 SSH 接口设置中输入密码并启动。
* “等待 SSH”时查看 Wireshark 的认证错误、主机指纹和端口；命令行 ssh 能登录不代表 Wireshark 已配置好。
* 抓包保存在浏览器电脑，不在 Docker 宿主机；以 Web 显示的完整路径和 Wireshark 实际保存设置为准。
* 旧版客户端缺少窗口诊断、保存路径或状态回报时，需更新后端并重新安装本地启动器。

旧版脚本排查
----------------------------------------

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - 现象
     - 优先检查
   * - 找不到容器记录
     - 当前目录是否与创建容器时一致；``.frr_containers.tmp`` 是否存在。
   * - 同名容器或 netns 已存在
     - 核对现有容器、PID 和 netns 归属；不要直接覆盖同名映射。
   * - 容器没有业务接口或 IP
     - FRR 初始化使用 ``--net=none``；核对实验是否已连接接口并配置地址。
   * - 无法生成拓扑图
     - 检查 ``dot``、Docker 与 OVS 访问权限、容器清单和输出目录。
   * - 拓扑出现警告或缺少连线
     - 核对实际接口及 OVS ``external_ids``；查看采集期间容器是否重启。
   * - VPCS 创建失败
     - 检查本地镜像、sudo 权限、接口名占用、网络命名空间和状态文件。
   * - 协议邻居未建立
     - 按链路、地址、协议进程、配置顺序检查，再结合接口抓包定位。

建议收集的信息
----------------------------------------

报告 Web 问题时，提供复现步骤、访问端口、实验名称/ID、设备镜像、状态、部署日志和后端错误。
构建问题补充 Node.js/npm 版本；抓包问题补充 Wireshark 版本、会话状态和本地启动器日志。
分享日志前去掉访问令牌、密码及其他连接凭证。

旧脚本问题另需记录执行目录、完整命令、错误输出、镜像标签与版本；根据所用功能补充
``docker ps``、``ip netns list``、``ovs-vsctl show``、容器接口信息、FRR 状态、SVG 和报文文件。
